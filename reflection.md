One design decision I made was to keep the customer support agent modular by using separate tools for different tasks. For example, order tracking and refunds are handled through AgentCore Gateway, product and policy questions use the Knowledge Base, and loyalty calculations use the Code Interpreter. I chose this approach because it keeps each responsibility clear and makes the agent easier to test and troubleshoot.

One challenge I ran into was working with the restricted Udacity VocLabs environment. Some AWS permissions were limited, especially when creating the Knowledge Base and when using the browser tool. I also had to fix IAM permissions so the deployed AgentCore runtime could retrieve information from the Knowledge Base and start browser sessions. Another small challenge was making sure the loyalty discount response used the exact values returned by the Code Interpreter instead of letting the model recalculate them. I resolved these issues by checking the actual error messages, updating only the required IAM permissions, and testing each feature separately before moving on.

For production, security and monitoring would be very important. In this project, the Gateway uses a NONE authorizer because it is a temporary learning environment, but I would not use that setup in production. I would require proper authentication, use least-privilege IAM roles, and avoid giving the agent access to unnecessary resources. I would also enable detailed monitoring and logging so failed tool calls, unusual activity, and latency issues could be detected quickly. Cost would also need to be monitored because services such as Bedrock, AgentCore, Knowledge Bases, and browser sessions can become expensive at scale.
